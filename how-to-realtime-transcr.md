# Transcription — Live Transcription Mode (macOS)

## TL;DR
- Task #12: an optional second recording mode that shows a real-time draft of the conversation — "Them" (system audio) and "Me" (microphone) — as interleaved `Them: …` / `Me: …` lines in a side panel while recording, alongside the unchanged post-recording pipeline.
- Mode selection: idle Record button now opens a popover (`RecordingModePicker`) offering "Default (simple transcription)" or "Live Transcription"; either starts recording immediately via `RecorderViewModel.start(mode:)`. Default mode is byte-for-byte unchanged.
- "Them" audio source is a SECOND, independent Core Audio process tap (`LiveSystemAudioTap`), not a tee off `SystemAudioRecorder` — isolation over DRY so a live-tap failure can never touch `system.wav`.
- "Me" source is a SECOND, independent `AVAudioEngine` input tap (`LiveMicAudioTap`), not a tee off `MicRecorder` — same isolation-over-DRY rationale; if it fails to start, live mode degrades to Them-only with a panel notice instead of failing.
- `LiveAudioChunker` (pure, `SplitVoxTranscription`) windows the live stream into 4.0s chunks overlapping by 1.0s, with a VAD gate that drops silent windows before decode.
- `WhisperTranscriber.transcribeChunk` decodes one window with the same anti-loop decode params as the batch path, in its own `whisper_context`.
- `LiveTranscriptionEngine` (@MainActor) owns both taps, one `LiveChunkFeeder`/chunker per speaker, one shared `AsyncStream<LiveSpeakerChunk>` with `.bufferingNewest(6)`, and a single detached decode worker that decodes chunks in arrival order and coalesces consecutive same-speaker text into one line; publishes status and draft lines to `LiveTranscriptPanel`.
- This is the one sanctioned exception to "only one Metal context should be resident at a time" (see ../README.md Invariants): the live engine's context is independent of `TranscriptionCoordinator`/`isBusy` and may run concurrently with a post-recording transcription.
- Draft text is never written to disk and never replaces `transcript.md`; it is a live approximation only, expected to differ from the final merged transcript.
- Any live-mode failure (model load, tap start, repeated decode failures) shows a panel warning but never stops or invalidates the recording.
- Task #13: text-level echo suppression gates decoded Me segments against a sliding window of recent Them texts using word-bigram containment against the concatenated Them corpus; segments with ≥55% bigram containment are suppressed before coalescing/publishing. Text is normalized (lowercased, punctuation stripped) before comparison. Pure functions live in `SplitVoxTranscription/EchoSuppression.swift`; ring buffer and gate logic in `LiveTranscriptionEngine`.
- Windows: not implemented; out of scope for this task.
- Key files: app/Sources/SplitVox/UI/RecordingModePicker.swift, app/Sources/SplitVox/Audio/LiveSystemAudioTap.swift, app/Sources/SplitVox/Audio/LiveMicAudioTap.swift, app/Sources/SplitVoxTranscription/LiveAudioChunker.swift, app/Sources/SplitVoxTranscription/WhisperTranscriber.swift, app/Sources/SplitVoxTranscription/EchoSuppression.swift, app/Sources/SplitVox/Transcription/LiveTranscriptionEngine.swift, app/Sources/SplitVox/UI/LiveTranscriptPanel.swift, app/Sources/SplitVox/UI/ContentView.swift, app/Sources/SplitVox/UI/RecorderViewModel.swift, app/Sources/SplitVoxCheck/main.swift

## Purpose

Give the user a real-time, low-latency view of the whole conversation — both what the other side ("Them") is saying and what the user ("Me") is saying — while a meeting is still recording, so note-taking and non-native listeners aren't stuck waiting for the recording to end. Live text is a best-effort DRAFT; the authoritative, fully-merged Me/Them transcript is still produced by the unchanged post-recording pipeline documented in ../README.md.

## Core Concepts

- **Mode selection**: `RecordingMode.standard` / `.liveTranscription`, chosen once per recording via `RecordingModePicker`'s popover on the idle Record button; the button reverts to a plain stop control once recording starts.
- **Second tap**: `LiveSystemAudioTap` reuses `SystemAudioRecorder`'s AudioCap-style pattern (private process tap + private aggregate device, `SystemAudioRecorderError`, `CoreAudioProperty`) but is a wholly separate object instance, converting to 16kHz mono Float32 and delivering samples via closure on its own serial queue. Same "Screen & System Audio Recording" permission; no new OS prompt.
- **Mic tap**: `LiveMicAudioTap` is its own `AVAudioEngine` + `AVAudioConverter` input tap, converting to 16kHz mono Float32 and delivering samples via closure on the render callback thread; reuses `MicRecorderError`. Same microphone permission as `MicRecorder`; no new OS prompt.
- **Chunker**: `LiveAudioChunker` is a pure, `Sendable` struct — fixed windows, overlap, RMS-based silence skip, `flush()` for the trailing partial window at stop, `reset()` to discard buffered audio across a pause/resume.
- **Chunk decoder**: `WhisperTranscriber.transcribeChunk(samples:language:)` — same greedy/no-context/RMS/no-speech gates as `transcribeWithStats`, but no leading-silence trim, no stats, and a lighter thread count to leave CPU for the meeting app itself.
- **Engine**: `LiveTranscriptionEngine` wires each tap into its own `LiveChunkFeeder` (lock-guarded chunker + paused flag), both feeding one shared `AsyncStream<LiveSpeakerChunk>` with `.bufferingNewest(6)`, consumed by a single detached worker holding its own `WhisperTranscriber`/`whisper_context`. The worker decodes chunks in arrival order, coalescing consecutive same-speaker text into the previous line rather than always starting a new one, and publishes `Status` (idle/loadingModel/listening/paused/interrupted(reason)).
- **Panel**: `LiveTranscriptPanel` is a 340pt right-side panel (`ContentView` is now an `HStack` of main column + conditional panel), visible only while `recorder.isRecording && activeMode == .liveTranscription`; each line renders as a bold speaker label (`Them: ` / `Me: `) followed by its text; header shows status + pause/resume + Copy All, which produces `Them: …\nMe: …` lines; body auto-scrolls to newest line unless the user has scrolled up, and watches `.onChange(of: engine.lines)` rather than `.count` since coalescing grows the last line in place without adding a new element.
- **Echo suppression** (task #13): when speakers are active (no headphones), the mic picks up Them audio and Whisper transcribes it as Me, producing duplicates. After a Me chunk is decoded but before coalescing/publishing, the engine normalizes the text (`EchoSuppression.normalizeForComparison` — lowercased, punctuation stripped, trimmed), concatenates all `recentThemTexts` entries (sliding window of the last ~20s), and computes word-bigram containment via `EchoSuppression.ngramContainment`. If ≥ `echoContainmentThreshold` (0.55) of Me's bigrams appear in the Them corpus, the Me segment is suppressed. This approach catches partial echoes (Me is a substring of Them) and cross-chunk echoes (echo spans two Them chunks) that per-chunk whole-string comparison misses. Them texts are recorded via `recordThemText` on each Them decode. Constants (`echoWindowDuration`, `echoContainmentThreshold`, `echoNgramSize`) are at the top of `LiveTranscriptionEngine` for tuning.

## Invariants

- The recording pipeline (`MicRecorder`, `SystemAudioRecorder`, `RecordingSession`, `WAVWriter`, `TranscriptionPipeline`, `TranscriptionCoordinator`, `TranscriptMerger`) is untouched by this task; `mic.wav`/`system.wav`/`session.json`/`transcript.md` behave exactly as in Default mode. `LiveMicAudioTap` is a separate `AVAudioEngine` instance from `MicRecorder`'s and never touches it; `mic.wav` is still recorded by `MicRecorder` exactly as before.
- The live engine's `whisper_context` is a separate, independent context from the one `TranscriptionCoordinator` uses for post-recording transcription; `TranscriptionCoordinator.isBusy` does not gate it, by design.
- Draft text lives only in `LiveTranscriptionEngine`'s in-memory published lines; it is never persisted and never feeds back into `transcript.md`.
- A live-mode failure (model load, tap start, 3 consecutive chunk decode failures) transitions the engine to `.interrupted` and surfaces a panel warning; it never stops, invalidates, or alters the underlying recording.
- Speaker attribution in the draft is by capture source — which tap the chunk arrived from — never ML diarization, mirroring the post-recording Me/Them principle.
- Mic-tap failure to start sets `engine.isMicUnavailable` and degrades to Them-only (panel shows "Microphone unavailable for the live draft — showing Them only"); only system-tap failure, model-load failure, or repeated decode failures trip `.interrupted`.
- Silence never reaches the GPU: a window's RMS is checked before decode, not after.
- `RecorderViewModel.stop()` calls `liveTranscription.stop()` before `session.stop()`/the post-recording transcription kicks off; the live worker is cancelled and frees its context at its next chunk boundary, so the two contexts may overlap for at most one chunk decode (independent contexts, so this is a resource overlap, never a correctness issue).
- No transcript text (draft or final) is ever logged at default visibility; live logging uses `SplitVoxLog.transcription`/`.pipeline`/`.capture` for lifecycle/status only. The one exception: echo-suppression debug logs include the first 40 chars of the matched Them text interpolated with `privacy: .private` (redacted unless the device explicitly reveals private os_log data).

## Route-Specific Constraints

- macOS only; requires the same "Screen & System Audio Recording" permission as Default mode's `SystemAudioRecorder`, no additional prompt.
- Chunk window 4.0s (`LiveAudioChunker.defaultChunkDuration`) overlapping 1.0s (`defaultOverlapDuration`) → 3s of new audio decoded per window; latency budget is ≤3s window fill + one decode.
- Silence gate reuses `WhisperTranscriber.silenceRMSThreshold` (0.005); a skipped silent window does NOT carry its overlap forward into the next window (deliberate: avoids re-decoding stale silence-adjacent audio).
- `flush()` at stop only emits a trailing window if ≥1s of new audio (`minimumFlushDuration`) and non-silent, since whisper.cpp rejects sub-1s input.
- `reset()` on resume-from-pause discards all pre-pause buffered audio so a paused stretch never leaks into the next window.
- `AsyncStream<LiveSpeakerChunk>` uses `.bufferingNewest(6)` (up from 4 now that there are two sources, sized for ~3 windows per source): if decode falls behind real time, the OLDEST undecoded windows are dropped so the panel stays close to live rather than catching up on a backlog.
- `transcribeChunk` sets `n_threads = max(2, cores/2)`, intentionally leaving CPU headroom for the meeting app, unlike the batch decoder.
- Overlap dedup: the engine drops any decoded segment whose `end <= overlapDuration` (already emitted by the previous window); segments straddling that boundary are kept as-is, so minor duplicated words/phrases at window boundaries are an accepted trade-off, not a bug.
- 3 consecutive chunk decode failures (`maxConsecutiveChunkFailures`) trips `.interrupted`; a `generation` counter makes any late worker callback after stop/restart a no-op.
- Line coalescing: decoded text is appended to the previous line when the speaker matches, else a new `Speaker: ` line starts; ordering is chunk arrival order across both streams, so a Me chunk and a Them chunk that overlap in real time may render in either order — accepted draft-quality trade-off.
- Pause/resume applies to both feeders together; there is no per-speaker pause.
- Echo suppression (`echoWindowDuration = 20.0`, `echoContainmentThreshold = 0.55`, `echoNgramSize = 2`): only Me segments are gated; Them path is never modified. The containment check is O(q + c) where q = Me word count, c = concatenated Them word count (hash-set build + lookup) — no heavy allocations, no worker blocking beyond the MainActor hop that already happens for `appendText`. The `recentThemTexts` ring buffer is pruned on each Them insert; cleared on `start()`. Text is normalized with `EchoSuppression.normalizeForComparison` (lowercased, punctuation stripped) so "другие." matches "другие".
- `EchoSuppression` (`normalizeForComparison`, `ngramContainment`, `textSimilarity`) — pure static methods in `SplitVoxTranscription` (not the app target) so they can be called from `SplitVoxCheck` for testing without importing the app.

## Known Failure Modes

- Not verified: an actual live GUI recording session end-to-end (both the process tap and the mic engine tap coexisting with the recorder's own taps in the real app, real-time decode latency on large-v3-turbo) — flagged as an open risk, not yet exercised outside `SplitVoxCheck`'s pure/e2e checks.
- Not verified: a second `AVAudioEngine` instance tapping the default input device concurrently with `MicRecorder`'s engine in a real GUI session (compiles; not exercised live).
- CPU/GPU contention is possible when a live session's decode worker runs concurrently with a different session's post-recording pipeline (two independent Metal contexts resident at once); accepted, correctness is unaffected since the contexts don't share state.
- Under sustained slow decode, `.bufferingNewest(6)` silently drops older windows — the draft can visibly skip ahead rather than lag indefinitely.
- Boundary word/phrase duplication across adjacent windows is possible when a segment straddles the overlap cutoff; not deduped beyond the `end <= overlapDuration` rule.
- If the whisper model is missing/unreadable, the engine goes straight to `.interrupted` with a warning; the recording proceeds with no live panel content at all.
- Cross-talk: simultaneous Me/Them speech is decoded per stream, so turns can appear reordered relative to real time.
- `SplitVoxCheck` (28 checks total) covers the chunker's pure logic (`runLiveAudioChunkerChecks`, 7 checks) and one tiny-model chunk-decode check (`runLiveChunkTranscribeCheck`, skips if the test model is absent); neither exercises the live tap or the full engine.
